# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

"2FA Login Request" (repo name `duty-roster`): a daily duty rotation for a Singapore team. Each working day everyone available gets a role (Primary, Secondary 1, 2…); the Primary is the person others ask for an OTP login. Plain HTML + ES modules, no build step, served by GitHub Pages from `main` at the repo root. Supabase (Postgres + auth) is the backend.

## Commands

```bash
npm start                     # serve on http://localhost:5173 (http-server, no caching)
npm test                      # node --test: runs every tests/*.test.mjs (store tests fake localStorage to drive DemoStore)
node --test --test-name-pattern "midnight" tests/schedule.test.mjs   # one test
npm run stamp                 # REQUIRED before every commit that changes a page, script or styles.css
node scripts/ui-check.cjs      # clicks through both pages in a real browser (demo mode); run before publishing UI changes
```

There is no linter, formatter or bundler.

`scripts/ui-check.cjs` is the functional check for the pages: it serves the site itself with an empty `config.js`, pins the clock, and uses Playwright to carry out every action (add and remove leave, end leave early, reorder, deactivate, rename, holidays, the public switch, restarting the rotation, sign-up and approval, month and tab navigation, swiping, reduced motion, a day when nobody is available, outside office hours, the card redrawn by a routine refresh), checking the roster and the public page after each. Playwright is not a dependency of the site; it is preinstalled in Claude Code cloud sessions. It only covers demo mode: nothing here exercises the real database, so changes to `SupabaseStore` or the SQL still need checking against the live project by the owner. When the UI changes, update its selectors and expectations in the same commit.

`npm run stamp` (`scripts/stamp.mjs`) rewrites the `<!-- version:start -->…<!-- version:end -->` block in `index.html` and `calendar.html`: an import map that gives every `src/*.js` and `config.js` a `?v=<YYYYMMDDHHMM>` suffix, plus the stylesheet and entry script. It picks up new files in `src/` automatically. Without it, phones mix cached old modules with new ones. `src/live.js` also reads this `?v=` stamp to detect that a newer version has been published.

## Publishing and going back

- `main` is the live site. A push to `main` is published within about a minute by the "pages build and deployment" Actions run. There is no staging copy, so build on a branch and let the owner see the change first (screenshots, or the pages served in demo mode) before anything goes to `main`.
- The `v1` branch is a checkpoint of the site as it was before the November 2026 redesign. Keep it. To go back, restore the site files from it in a new commit on `main` and run `npm run stamp`; don't rewrite `main`'s history. It is a branch because a tag push was refused from a cloud session.
- Cloud sessions may be unable to reach the live site, Supabase, or the jsdelivr CDN the Supabase client loads from. If so, confirm a publish from the Actions run, say plainly that the live site and real database were not checked, and ask the owner to check them.

## Architecture

**Two pages, two entry scripts**
- `index.html` → `src/app.js`: the signed-in app (Roster, Leave, Team & settings tabs). Renders with template strings into `#root`; `refresh()` reloads all data and redraws; `act(fn, message)` wraps every write (disables the triggering control, toasts, refreshes, restores focus via `focusKey`/`restoreFocus`).
- `calendar.html` → `src/calendar.js`: the public page, no login. Two tabs (2FA Login card, and Calendar Forecast month grid; `#calendar` in the URL opens the second). The page only ever receives names and roles, never leave, emails or ids.
  - The 2FA Login card leads with the answer: the room scene on top, then the Primary's face and name, the Secondaries, and the WhatsApp button. `src/engineer.js` draws the scene, picked by Singapore time (`periodAt`): six weekday scenes, and the lights off on weekends and public holidays; `?scene=lunch` etc. forces one for previews. It is one room with a sky, lighting and pose per scene, and its wall clock shows the real Singapore time. Today's date is an HTML sign over the scene (`.wall-date`), not part of the SVG.
  - The Secondaries are on the same card, as a rail: a line drops from the Primary's face, turns, and runs through each Secondary in backup order (`relay()` in `calendar.js`; `.stem`, `.relay` and `.rail` in `styles.css`). The Primary's name stands beside the face (`.hero-lead`), with the scene's caption on the scene's floor above it. The owner tried the alternatives (the Primary block as it was before, with the rail under the name) and chose this layout, with one condition: the Primary's circle keeps the size it had before (`--av`: 5.5rem, 7rem on wide cards, 5rem only on the narrowest phones), so don't shrink it. One or two stand with their names beside them (`.pairs`); three or more have their names under the faces and wrap into rows that branch off the same line. The card is a CSS container (`@container card`), so how many stops share a row, and every size, follows the card's own width rather than the screen's: `relay()` passes the row lengths for the three widths (cards under 340px: three stops to a row; other phones: four; cards of 520px and up: six) as `--cn`/`--cp`/`--cw` and marks the stops that start a row with `--sn`/`--sp`/`--sw`. `fitNames()` measures the names after every draw and resize: it drops the side-by-side layout, then switches the whole rail to first names (`.short`, then `.tight`), when full names don't fit. It can't measure a hidden tab, so `setTab()` calls it again. Stops are steel blue (`--steel`), never cyan.
  - Motion on the card: the first draw plays an entrance once (`.enter` on `#today`, set by the `drawn` flag in `calendar.js`). After that the Primary's ring glows and a glint runs along the rail every 5 seconds; the owner chose that interval. The three animations (`halo`, `glint`, `ping`) share the duration and their keyframe percentages are worked out for it, so changing the duration alone also changes how fast the movement is. The glint crosses one stretch of line in .27s, which is also the delay step from one stop to the next. The same cycle runs on the smaller rail in the "Next on duty" box, where the next Primary's small ring glows instead of the big face's. A refresh redraws the card without `.enter`, and that changes more than the motion: while the entrance animations are in effect (they fill `both`) the animated elements are containing blocks, and afterwards they are not. The glint in the side-by-side layout once escaped its line that way, so look at the card after a redraw as well as on first draw (`ui-check` does, in its last-but-one section).
  - On a working day when nobody is available the card says so instead: the lights-off scene (`nobody`), a red "No duty cover today" label, "No one is available for duty." with no face, and the button reads "Tell the team on WhatsApp" (same link; the message already says no one is available).
  - Office hours are 9am to 6pm on working days (`OFFICE_OPEN`/`OFFICE_CLOSE`, `officeHours()` in `schedule.js`). Outside them the card says "Outside office hours · No one is on duty now.", shows the lights-off `closed` scene and a "Next on duty · 9am today/tomorrow/<date>" box (that day's Primary, with their Secondaries on a smaller rail), and the button reads "Tell the team on WhatsApp". From 6pm the next cover, Secondaries, Up next and WhatsApp message move to the next working day. Both pages switch over by themselves at 9am and 6pm (`msUntilOfficeChange()`); the signed-in Roster card does the same, with a note. Weekends and public holidays use the same layout, with a red "No duty today" label and the reason. Office hours are a display rule only: the rotation, the database and `public_calendar()` are unchanged.
  - Beside the card (below it on phones): an "Up next" timeline of the Primary for the next three working days (names only; one dot per day on a line, drawn with `li::before`/`li::after` in `styles.css`: today's dot is filled cyan, a day with nobody gets a red one), and a red "No one is available on:" card listing upcoming working days whose duty list is empty.
  - The Calendar Forecast lists everyone available on each day, names only, Primary first in a pill. From today on, a dashed slot stands for each person missing from that day (team size is `people.length` from `public_calendar()`); earlier days get no slots because the team may have been smaller then. A week with no weekday in the month is left out. Today's cell says "Today" and glows; at the weekend, when today has no cell, a note above the grid says so and the next weekday is marked "Next".
  - It asks `loadPublic(today, today + 60)`. The SQL `public_calendar()` silently clips every request to at most ~62 days and to 90 days back / 180 days ahead, so asking for more just returns fewer days.
  - On phones the Calendar Forecast prints each name twice (`.full` and `.first` spans) and CSS shows the short one only; wording changes touch both. `shortName()` in `schedule.js` gives the first name, or the full name when two people share a first name.
- Headers have no title: one row with the tab pill, then on the right a "Sign in" link (calendar.html) or, in the app, a round button with your face whose menu (`toggleAccount` in app.js) holds who is signed in, Calendar and Sign out. Tab labels too long for phones carry `.tab-long`/`.tab-short` spans (e.g. "Calendar Forecast"/"Forecast", admins' "Team & settings"/"Team").

**Shared UI pieces across the two pages** — the WhatsApp button label is written in both `app.js` and `calendar.js` ("Click for OTP on WhatsApp", or "Tell the team on WhatsApp" when the day shown has nobody on duty); its icon (`WHATSAPP_ICON`), link and message text (`rosterMessage`) live in `schedule.js`. People are shown the same way on both pages: a drawn face in a circle (`.av`), made from their name by `src/faces.js` (the same name always gets the same face, and nothing is sent to an outside avatar service), with a cyan ring for the Primary. `faces.js` picks each part by a hash of the name, modulo the length of that part's list, starting from a fixed `SEED`: changing `SEED`, or adding, removing or reordering entries in its palettes or style lists, changes almost everyone's face. The Calendar Forecast and the Up next strip use names only, with no faces. The signed-in Roster tab shows your role with that day's line-up as a strip (`lineup()` in `app.js`), then one row per working day: the Primary, "then" the backups in order, anyone on leave, and your own role as a badge.

**Wording** — all UI text is plain, friendly, sentence case and short. Several strings are asserted exactly, so a wording change means updating them too: `rosterMessage()` in `tests/schedule.test.mjs`; toasts, labels and the WhatsApp button in `scripts/ui-check.cjs`; and `DemoStore`'s error messages, which copy the database's.

**Data layer** — `src/connect.js` returns `SupabaseStore` when `config.js` has a URL and anon key, otherwise `DemoStore` (localStorage, five example people). Both live in `src/store.js` and expose the same methods. `DemoStore` deliberately mirrors the database's row-level security and triggers (admin checks, leave rules) so demo mode fails the same way production does; keep them in step. In `SupabaseStore`, updates and deletes end in `.select()` and go through `changed()`, because RLS silently skips forbidden rows and `protect_profile_fields()` silently reverts non-admin field changes — `updateProfile` compares the returned row to the patch to catch that.

**Rotation logic** — `src/schedule.js` is pure (no DOM) and fully unit-tested: `buildSchedule` walks working days from the first **rota checkpoint**, skipping weekends, holidays and people on leave. Checkpoints (`rota_checkpoints` table) freeze history: approving, deactivating or reordering people saves a checkpoint dated today (`recordRotaChange` in app.js), so earlier days keep their duties. The same algorithm is reimplemented in SQL as `public_calendar()` (supabase/004_stable_history.sql) for the public page — a change to the rotation rules must be made in both. `rosterMessage()` builds the WhatsApp text (its exact wording is asserted in tests).

**Public holidays** — `schema.sql` seeds the `holidays` table and `src/holidays-sg.js` seeds demo mode, both with 2026–2027 from the Ministry of Manpower dataset (data.gov.sg collection 691). Later years are added by admins in the Team tab, not in code.

**Time** — everything uses Singapore dates: `todaySG()` in JS, `public.sg_today()` in SQL. Dates are `YYYY-MM-DD` strings; `fromISO` parses at noon to avoid DST/offset slips.

**Staying fresh** — `src/live.js` `keepFresh()` re-fetches when the page becomes visible, every 5 minutes, and just after Singapore midnight; app.js skips it while a form has unsaved input. It also shows a "new version available" bar when the published page's stamp differs.

**Swiping** — `src/swipe.js` (both pages): on phones a sideways swipe clicks the next or previous `[data-tab]` button and slides the new content in; it ignores the screen edges, form fields and (in app.js) unsaved input. The first visit on a phone plays a one-time "peek" at the next tab (remembered in localStorage as `swipePeekSeen`).

**Styles** — one `styles.css`, the "Ocean" theme: always dark, deep sea blue, flat panels, tokens on `:root`, Plus Jakarta Sans + JetBrains Mono from Google Fonts. Cyan (`--accent`, `--primary`) means "Primary" or "today" and nothing else; leave is purple, holidays green, gaps red, and the WhatsApp button is bright green with dark text (`--wa`, `--wa-ink`). Animations must stop under `prefers-reduced-motion` (one rule on `.hero-card *` switches off everything on the card). A theme change is more than the `:root` tokens: `styles.css` also hard-codes a few colours (header, selected tab, the red gaps card), `faces.js` hard-codes the face palettes, and `engineer.js` hard-codes the room, sky and padlock colours; only the engineer's hoodie follows the tokens (`--hoodie*`).

## REBUILD.md

`REBUILD.md` is a standalone spec for recreating the app from scratch (rotation rules, schema, UI, theme). Nothing loads it. When behaviour, layout or theme changes, update its matching section in the same commit so it doesn't drift.

## Database (supabase/)

SQL is not applied automatically: the project owner pastes each file into the Supabase SQL Editor. New installs run `schema.sql`, then `003_private_data.sql`, `004_stable_history.sql`, `006_hardening.sql`, `011_leave_invites.sql` (the README lists the order). `002_public_calendar.sql` is only for databases created before the public calendar became part of `schema.sql`. Numbers 005, 007 and 009 were features that were later removed; `008_remove_calendar_sync.sql` and `010_remove_daily_email.sql` undo them on databases that ran them, which is why those files are absent.

- Never edit a migration the owner may already have run; add the next numbered file, make it safe to run twice (`if exists`, `create or replace`, `drop policy if exists`), and update the README's setup list.
- Front-end code that depends on a new migration should be published only after the owner confirms it ran.
- Access is enforced by RLS plus `security definer` functions with explicit `revoke … from public, anon` / `grant` lines; emails and leave notes are hidden by column grants and exposed only through `member_emails()` / `leave_notes()`.
- **Leave from invites** (`011_leave_invites.sql` + `scripts/leave-invites.gs`): a Google Apps Script in a shared Google account reads the invite *emails* (their `invite.ics` attachments: ORGANIZER, dates, SEQUENCE, METHOD:CANCEL) and posts every current leave-like invite to `sync_leave_invites(secret, events)` every 15 minutes. It reads Gmail, not the calendar, because Google imports Outlook invites as events owned by the account itself, which hides the organiser. The list is complete, so invites missing from it count as cancelled; invite leave is keyed by `leaves.invite_uid` (private; the app sees only `from_invite`). Matching uses `profiles.work_email` (private, via `member_work_emails()` / `set_work_email()`) or the sign-in email; misses go to `unmatched_invites` for admins. Removing invite leave in the app would be undone by the next sync, so the UI points people to Outlook instead.
  - What counts as leave is decided in the script (`parseInvite`): all-day events, events of 20 hours or more, and Out of office events (`X-MICROSOFT-CDO-BUSYSTATUS: OOF`) of 4 hours or more. Ordinary meetings are ignored. Leave is whole days only, so a 4-hour Out of office invite takes the person off the roster for that entire day.
  - `set_work_email()` lets approved members set their own and admins set anyone's; people awaiting approval and the public page are refused (`DemoStore.setWorkEmail` mirrors this).
  - The script runs in Google, not from this repo: pushing a change to `scripts/leave-invites.gs` deploys nothing. The owner must paste the new version into script.google.com in the shared account. The committed file keeps `SCRIPT_SECRET = 'paste-the-script-secret-here'`; the real secret (from `invite_config`) only goes into the Google copy.
- `config.js` holds the real project URL and anon key (public by design). To exercise the UI in demo mode, serve the site with an empty `config.js` (e.g. a browser-automation route override) rather than editing the committed file.
