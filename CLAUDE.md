# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

"2FA Login Request" (repo name `duty-roster`): a daily duty rotation for a Singapore team. Each working day everyone available gets a role (Primary, Secondary 1, 2…); the Primary is the person others ask for an OTP login. Plain HTML + ES modules, no build step, served by GitHub Pages from `main` at the repo root. Supabase (Postgres + auth) is the backend.

## Commands

```bash
npm start                     # serve on http://localhost:5173 (http-server, no caching)
npm test                      # node --test: runs every tests/*.test.mjs (store tests fake localStorage to drive DemoStore, and a stand-in Supabase client for SupabaseStore; dates.test.mjs runs in-process under several time zones)
node --test --test-name-pattern "midnight" tests/schedule.test.mjs   # one test
npm run stamp                 # REQUIRED before every commit that changes a page, script or styles.css
node scripts/ui-check.cjs      # clicks through both pages in a real browser (demo mode), several minutes; run before publishing UI changes
node scripts/shots.cjs --out <folder>   # pictures of every state of the 2FA Login card, to show the owner before publishing
```

There is no linter, formatter or bundler.

`scripts/ui-check.cjs` is the functional check for the pages (204 checks): it serves the site itself with an empty `config.js`, pins the clock, and uses Playwright to carry out every action on both pages, checking the roster and the public page after each. Later sections fake trouble: R seeds its own rotation history; N (the signed-in app) runs on a wrapped `store.js` that can be slowed or made to fail (`__delay`, `__fail`); S, T and U (the public page) use a stand-in `connect.js` (`flaky`) whose CDN download fails on demand (`cdn.down`), with the store as `__store`. Playwright is preinstalled in Claude Code cloud sessions, not a dependency of the site. It only covers demo mode, so changes to `SupabaseStore` or the SQL still need checking against the live project by the owner. When the UI changes, update its selectors and expectations in the same commit.

`scripts/shots.cjs` makes the pictures the owner sees before a change is published. Like `ui-check` it runs the pages in demo mode with a pinned clock and needs Playwright, but it uses no port (the browser is handed the files from disk), so several runs can go at once. A plain run takes about a minute: every state of the 2FA Login card on a phone (`open-4`, `open-2` (the size of the real team), `open-1`, `open-0`, `open-6`, `long`, `short`, `lunch`, `afternoon`, `evening`, `before`, `after`, `after-2`, `weekend`, `holiday`, `nobody`, `nobody-next`), and the ones that stress the layout at 320px, tablet and desktop width. `--only` and `--views` narrow it (`p360`, `p375` and `p412` are further phone widths), and `--page forecast|signin|roster|leave|team` shoots the other screens. For each picture it prints where the WhatsApp button ends, sideways scrolling and browser errors, and it writes an overview sheet per width.
- Before and after: extract the live version (`mkdir <dir> && git archive origin/main | tar -x -C <dir>`), shoot it with `--root <dir>`, then shoot the working copy with `--compare <the folder of before pictures>`; each `compare-*.png` is ready to send.
- `--redraw` shoots the card after the 5-minute refresh, which now redraws only when something changed, so with demo data it shows the first draw (its help text is out of date). `--at <ms>` freezes its animations at one moment so two runs can be compared.
- Send the output to a folder outside the project (the session's scratchpad): GitHub Pages serves every file in the repo.

`npm run stamp` (`scripts/stamp.mjs`) rewrites the `<!-- version:start -->…<!-- version:end -->` block in `index.html` and `calendar.html`: an import map that gives every `src/*.js` and `config.js` a `?v=<YYYYMMDDHHMM>` suffix, plus the stylesheet and entry script. It picks up new files in `src/` automatically. Without it, phones mix cached old modules with new ones. `src/live.js` also reads this `?v=` stamp to detect that a newer version has been published.

## Publishing and going back

- `main` is the live site. A push to `main` is published within about a minute by the "pages build and deployment" Actions run. There is no staging copy, so build on a branch and let the owner see the change first (before-and-after pictures from `scripts/shots.cjs`, or the pages served in demo mode) before anything goes to `main`. The owner is not a developer and judges on a phone, so show phone pictures first.
- The `v1` branch is a checkpoint of the site as it was before the November 2026 redesign. Keep it. To go back, restore the site files from it in a new commit on `main` and run `npm run stamp`; don't rewrite `main`'s history. It is a branch because a tag push was refused from a cloud session.
- Cloud sessions may be unable to reach the live site, Supabase, or the jsdelivr CDN the Supabase client loads from. If so, confirm a publish from the Actions run, say plainly that the live site and real database were not checked, and ask the owner to check them.

## Architecture

**Two pages, two entry scripts**
- `index.html` → `src/app.js`: the signed-in app (Roster, Leave, Team & settings tabs). Renders with template strings into `#root`. `refresh()` reloads all data and redraws; only the latest refresh draws.
  - `act(fn, message)` wraps every write: it disables the control actually used and its form (`trigger`, from capture listeners, because Safari doesn't focus tapped buttons; no global busy guard), toasts, refreshes, and restores focus (`focusKey`/`restoreFocus`) unless it has moved on. A refused save keeps what was typed and says why once (`formError`, `role="alert"`, or a toast for ticks); offline it first redraws from the last good data, so ticks revert. Submit buttons have ids; fields are 16px so iPhones don't zoom.
  - Nothing redraws under typing (`typing()`: changed text or a focused text box, not a focused tick): swipes wait, and a background refresh (keepFresh, 9am/6pm, `online`, a stale tab, a heal) parks its data in `pendingDraw` for `drawWhenIdle`, which draws it once no field holds unsaved text (or on a save or tab switch), never mid-tap. A new Singapore day is drawn at once, typing or not (`#view[data-day]`), because the view's buttons carry its dates; End early uses `today()` itself. `redraw()` keeps typed values, focus and caret.
  - Offline: `plain()` words, the `#offline` bar after a failed refresh, `cantLoad()` after a failed first load. `SupabaseStore.signOut` clears the stored session itself when the request fails (needs a live check).
  - The Roster opens at this week's Monday (next Monday at weekends) through at least next Friday. One-tap changes to someone else ask first, by first name. Remove access (owner's decision) unsets `approved`, `active` and `is_admin` and saves the rotation change; a "Removed" list offers "Give access again", and they see "Your access was removed". No one who was ever on the rotation can be deleted (it would rewrite past duties).
- `calendar.html` → `src/calendar.js`: the public page, no login. Two tabs (2FA Login card, and Calendar Forecast month grid; `#calendar` in the URL opens the second). The page only ever receives names and roles, never leave, emails or ids.
  - The 2FA Login card leads with the answer: the room scene on top, then the Primary's face and name, the Secondaries, and the WhatsApp button. `src/engineer.js` draws the scene, picked by Singapore time (`periodAt`): six weekday scenes, and the lights off on weekends and public holidays; `?scene=lunch` etc. forces one for previews. It is one room with a sky, lighting and pose per scene, and its wall clock shows the real Singapore time. Today's date is an HTML sign over the scene (`.wall-date`), not part of the SVG. Captions say what's true (owner's decision): lunch is "Lunch at the desk. Ask anytime.", the half hour before 6pm "Last stretch. On duty till 6pm." (not "wrapping up") ("Lunchtime / Still on duty" on the monitor), since duty includes lunch.
  - The card and the month load in parallel and fail independently, each with Try again ("Trying…", then "Still can't connect."); a failed refresh keeps what is shown. A failed Supabase client download (`getStore`/`storeBroken`) stays failed for the page's life, so `reloadIfBroken` reloads the page instead, but never offline.
  - The Secondaries are on the same card, as a rail: a line drops from the Primary's face, turns, and runs through each Secondary in backup order (`relay()` in `calendar.js`; `.stem`, `.relay` and `.rail` in `styles.css`). The Primary's name stands beside the face (`.hero-lead`), with the scene's caption on the scene's floor above it. The owner tried the alternatives (the Primary block as it was before, with the rail under the name) and chose this layout, with one condition: the Primary's circle keeps the size it had before (`--av`: 5.5rem, 7rem on wide cards, 5rem only on the narrowest phones), so don't shrink it. One or two stand with their names beside them (`.pairs`); three or more have their names under the faces and wrap into rows that branch off the same line. The card is a CSS container (`@container card`), so how many stops share a row, and every size, follows the card's own width rather than the screen's: `relay()` passes the row lengths for four widths (cards under 280px, i.e. zoomed text: two stops; under 340px: three; other phones: four; 520px and up: six) as `--ct`/`--cn`/`--cp`/`--cw`, and `--st`/`--sn`/`--sp`/`--sw` mark the stops that start a row; under 280px the WhatsApp label also wraps. `fitNames()` measures the names (from the layout, not as the entrance draws them) after every draw and resize: it drops the side-by-side layout, then switches the whole rail to first names (`.short`, then `.tight`), when full names don't fit, and `fitWords()` shrinks a name rather than break a word. It can't measure a hidden tab, so `setTab()` calls it again. Stops are steel blue (`--steel`), never cyan.
  - Motion on the card: the first draw plays an entrance once (`.enter` on `#today`, set by the `drawn` flag in `calendar.js`). After that the Primary's ring glows every 5 seconds (`halo`; the owner chose that interval), and in the "Next on duty" box the next Primary's small ring does the same. There is no glint along the line: the owner had it removed, so don't add one back. `drawToday()` redraws only when something besides the clock changed, so focus and animations survive: the hands move in place every minute (`clockHands`, `everyMinute`) and a new part of the day swaps only the scene. A redraw comes without `.enter`, and `setTab()` removes it when you leave the tab, so the entrance plays once. Losing `.enter` changes more than the motion: while the entrance animations are in effect (they fill `both`) the animated elements are containing blocks, and afterwards they are not. So look at the card without `.enter` as well as on first draw (`ui-check` L2 and M8 do).
  - On a working day when nobody is available the card says so instead: the lights-off scene (`nobody`), a red "No duty cover today" label, "No one is available for duty." with no face, and the button reads "Tell the team on WhatsApp" (same link; the message already says no one is available).
  - Office hours are 9am to 6pm on working days (`OFFICE_OPEN`/`OFFICE_CLOSE`, `officeHours()` in `schedule.js`). Outside them the card says "Outside office hours · No one is on duty now.", shows the lights-off `closed` scene captioned "Office closed. Opens at 9am tomorrow." (or Monday, or a date: the real next duty day; just "Office closed." when nobody is available then; owner's decision), a "Next on duty · 9am today/tomorrow/<date>" box (that day's Primary, with their Secondaries on a smaller rail), and "Tell the team on WhatsApp". From 6pm the next cover, Secondaries and Up next move to the next working day, but on both pages the WhatsApp message stays today's (owner's decision). Both pages switch over by themselves at 9am and 6pm (`msUntilOfficeChange()`); the signed-in Roster card does the same, with a note. Weekends and public holidays use the same layout, with a red "No duty today" label and the reason. Office hours are a display rule, with one exception: a team change after 6pm on a working day also keeps the next working day's announced Primary (`rotaChange(…, { afterHours })`, an extra checkpoint). `public_calendar()` and the database are unchanged.
  - Beside the card (below it on phones): "Up next", the Primary on each of the three working days after the one the card shows (the owner asked that it not repeat today), side by side in tiles (`.next-days`, `.next-duty`): the day ("Tomorrow", then "Wed 18") with a dot, and the first name. Every 5 seconds, just after the Primary's ring glows, a soft white glint crosses the tiles left to right, lighting each dot and edge as it passes (`duty-glint`, `duty-glow`, `duty-halo`, delayed by `--i`); white, not cyan, because cyan is today. A day with nobody is red, with no glint. The tiles stack only when a day doesn't fit at 340px and below, or a name below 300px (measured in `fitNames()`). Then a red "No one is available on:" card listing upcoming working days whose duty list is empty.
  - The Calendar Forecast lists everyone available on each day, names only, Primary first in a pill. From today on, a dashed slot stands for each person missing from that day (team size is `people.length` from `public_calendar()`); earlier days get no slots because the team may have been smaller then. A week with no weekday in the month is left out. Today's cell says "Today" and glows; at the weekend, when today has no cell, a note above the grid says so and the next weekday is marked "Next". `fitForecast()` sets names smaller (`.long-names`) only when one is cut.
  - State is `cal = { month, home, seq, busy }`; only the latest load is drawn. The refresh follows the current month, even with focus on a month button (`putView`). Prev and Next stop at `dataWindow` and the rotation's start (`.cal-note` says so); `#announce` reads out the month.
  - A working day with nobody available is a red cell (`.cell.gap`) with a warning sign and "No one available"; on today it keeps the cyan outline around the red.
  - Motion on the Forecast: the first time it is on screen the days ripple in from today's cell (`.cal.enter`; `--d` is each day's distance from today, from `--r`/`--c` on the cells and `--tr`/`--tc` on the grid); a change of month brings them in from the side it came from (`.from-next`/`.from-prev`); every 5 seconds, in step with the card, today's cell swells its glow and a glint passes under today's Primary's name (the "Next" cell at weekends only brightens its outline: a glow means today). A swipe into the tab brings its own slide, so `swipeTabs` drops the ripple then. `render()` skips a redraw that would change nothing, `calShown` keeps the ripple to the first showing, and `setTab()` strips the classes when you leave, so coming back doesn't replay it. The Forecast opens on the month of the next working day (`nextWeekday()`), which matters on a weekend at the end of a month. The entrances fill `backwards`, not `both`, so no cell is left transformed (see the card's note on redraws), and the month change moves only 20px because more makes the page scroll sideways.
  - It asks `loadPublic(today, today + 60)`. The SQL `public_calendar()` silently clips every request to at most ~62 days and to 90 days back / 180 days ahead, so asking for more just returns fewer days.
  - On phones the Calendar Forecast prints each name twice (`.full` and `.first` spans) and CSS shows the short one only; wording changes touch both. `shortName()` in `schedule.js` gives the first name, or the full name when two people share a first name.
- Headers have no title: one compact 48px row with the tab pill, then on the right a "Sign in" link (calendar.html) or, in the app, a round button with your face whose menu (`toggleAccount` in app.js) holds who is signed in, Calendar and Sign out. The controls look smaller than they answer: an invisible `::before` gives each tab, Sign in and the face a 44px tap inside the bar, so the pill keeps no overflow (it scrolls sideways only below 280px), and the phone's tap flash is off on them in favour of an `:active` style on the visible shape; `ui-check` A0 checks the height and the 320px fit. Tab labels too long for phones carry `.tab-long`/`.tab-short` spans (e.g. "Calendar Forecast"/"Forecast", admins' "Team & settings"/"Team").

**Shared UI pieces across the two pages** — the WhatsApp button label is written in both `app.js` and `calendar.js` ("Click for OTP on WhatsApp", or "Tell the team on WhatsApp" when no one is on duty now); its icon (`WHATSAPP_ICON`), link and message text (`rosterMessage`) live in `schedule.js`. In the app, today's Primary gets "Tell the team on WhatsApp" with no ask line (`rosterMessage(day, url, { ask: false })`). Both pages show people as a drawn face in a circle (`.av`), made from the name by `src/faces.js` (nothing is sent to an outside avatar service), with a cyan ring for the Primary. `faces.js` picks each part by a hash of the name, modulo the length of that part's list, starting from a fixed `SEED`: changing `SEED`, or adding, removing or reordering entries in its palettes or style lists, changes almost everyone's face. The Calendar Forecast and the Up next strip use names only, with no faces. The signed-in Roster tab shows your role with that day's line-up as a strip (`lineup()` in `app.js`), then one row per working day: the Primary, "then" the backups in order, anyone on leave, and your own role as a badge. You are never cyan (owner's decision): a white bold name, with no underline (it would read as a link); the Primary's tile has the cyan ring.

**Wording** — all UI text is plain, friendly, sentence case and short. Several strings are asserted exactly, so a wording change means updating them too: `rosterMessage()` and the scene captions in `tests/schedule.test.mjs`; toasts, labels, the WhatsApp button, the questions before changes, captions and the account screens in `scripts/ui-check.cjs`; and the refusal messages in `tests/store.test.mjs`.

**Data layer** — `src/connect.js` returns `SupabaseStore` when `config.js` has a URL and anon key, otherwise `DemoStore` (localStorage, five example people). Both live in `src/store.js` and expose the same methods. `DemoStore` deliberately mirrors the database's row-level security, triggers and constraints, with production's final messages, so demo mode fails the same way; keep them in step. The leave rules (`enforce_leave_rules()` in `006_hardening.sql`, `DemoStore.leaveRule`) bind non-admins only: leave is added from today on, at most 180 days long and up to a year ahead, and leave that has begun can be ended early but not deleted, nor its start moved. The first account to sign up becomes the admin (trigger in `schema.sql`). In `SupabaseStore`, updates and deletes end in `.select()` and go through `changed()`, because RLS silently skips forbidden rows (`NOT_SAVED`) and `protect_profile_fields()` silently reverts non-admin field changes — `updateProfile` compares the returned row to the patch to catch that (`ONLY_ADMINS`). `plainError`/`refused` put raw Postgres refusals into plain words in both stores and log the original with `console.warn` (its constraint name is the owner's clue to a migration not run).

**Rotation logic** — `src/schedule.js` is pure (no DOM) and fully unit-tested: `buildSchedule` walks working days from the first **rota checkpoint**, skipping weekends, holidays and people on leave. Someone on leave on their Primary turn misses it rather than anyone doing Primary twice in a row. Checkpoints (`rota_checkpoints` table) freeze history, and today's Primary stays as announced (`tests/history.test.mjs`):
- Approving, deactivating, reordering or removing people saves `rotaChange()`'s checkpoints (`recordRotaChange`). `checkpointFor()` builds on the rotation as it stands, so today's Primary stays and two changes in a day build on each other; with `{ afterHours }` (from 6pm on a working day) the next working day's announced Primary stays too.
- An admin's correction to past leave or holidays (`actPast`) asks first, then saves `pastEdit()`'s checkpoint on the day after the corrected days, so only those days change; a Primary recorded as away after the fact doesn't get the turn back.
- When the rotation and the team disagree (a lost save, a fresh install), an admin's page saves the change itself (`shouldHeal`, `healRotation`). Rotation writes take turns (`inTurn`). These are all ordinary checkpoints, which `public_calendar()` already reads: no migration was needed.
- Known limits: "End early (back today)" can still change today's Primary; and a weekend deactivate-and-reactivate normally gives the person their turn back, but not Monday's announced Primary once a Friday-evening change has saved Monday's checkpoint.

The one exception to frozen history is changing the rotation start in the Team tab (`resetRotation` in `store.js`): it replaces every checkpoint with one at the new start and recalculates all earlier days, which is why the app asks first (`restartNote`). Against the database that is three requests, ordered so a dropped connection never leaves the rotation without history (new checkpoint first, start date, old checkpoints cleared last); a test in `tests/store.test.mjs` drops the connection at each step. The same algorithm is reimplemented in SQL as `public_calendar()` (supabase/004_stable_history.sql) for the public page — a change to the rotation rules must be made in both. `rosterMessage()` builds the WhatsApp text (its exact wording is asserted in tests).

**Public holidays** — `schema.sql` seeds the `holidays` table and `src/holidays-sg.js` seeds demo mode, both with 2026–2027 from the Ministry of Manpower dataset (data.gov.sg collection 691). Later years are added by admins in the Team tab, not in code.

**Time** — everything uses Singapore dates: `todaySG(now)` in JS, `public.sg_today()` in SQL. Dates are `YYYY-MM-DD` strings. `todaySG` uses Singapore's fixed +8 offset, and `addDays`, `isWeekend` and `daysBetween` count in UTC, so every viewer's time zone gives the same answers (`tests/dates.test.mjs`); `fromISO` parses at local noon, for display.

**Staying fresh** — `src/live.js` `keepFresh()` re-fetches when the page becomes visible, every 5 minutes, and just after Singapore midnight; app.js refreshes even while someone is typing, but a background refresh never redraws under them (it holds the draw, `pendingDraw`, until they stop), and a new day is drawn at once even mid-typing (ui-check N29), so a half-typed note left overnight can't leave the page on yesterday; a refresh still running after 25 seconds is given up on. It also shows a "new version available" bar when the published page's stamp differs.

**Swiping** — `html, body { overflow-x: clip }` keeps the page from scrolling sideways while a tab slides in. `src/swipe.js` (both pages): on phones a sideways swipe clicks the next or previous `[data-tab]` button and slides the new content in; it ignores the screen edges, form fields and swipes while someone is typing (a focused tick doesn't count). The first visit on a phone plays a one-time "peek" at the next tab (remembered in localStorage as `swipePeekSeen`).

**Styles** — one `styles.css`, the "Ocean" theme: always dark, deep sea blue, flat panels, tokens on `:root`, Plus Jakarta Sans + JetBrains Mono from Google Fonts. Cyan (`--accent`, `--primary`) means "Primary" or "today" and nothing else (the one existing exception is the ring on your own face button in the app's header); leave is purple, holidays green, gaps red, and the WhatsApp button is bright green with dark text (`--wa`, `--wa-ink`). Animations must stop under `prefers-reduced-motion` (one rule on `.hero-card *` switches off everything on the card). A theme change is more than the `:root` tokens: `styles.css` also hard-codes a few colours (header, selected tab, the red gaps card), `faces.js` hard-codes the face palettes, and `engineer.js` hard-codes the room, sky and padlock colours; only the engineer's hoodie follows the tokens (`--hoodie*`).

## REBUILD.md

`REBUILD.md` is a standalone spec for recreating the app from scratch (rotation rules, schema, UI, theme). Nothing loads it. When behaviour, layout or theme changes, update its matching section in the same commit so it doesn't drift.

## Database (supabase/)

SQL is not applied automatically: the project owner pastes each file into the Supabase SQL Editor. New installs run `schema.sql`, then `003_private_data.sql`, `004_stable_history.sql`, `006_hardening.sql`, `011_leave_invites.sql` (the README lists the order). `002_public_calendar.sql` is only for databases created before the public calendar became part of `schema.sql`. Numbers 005, 007 and 009 were features that were later removed; `008_remove_calendar_sync.sql` and `010_remove_daily_email.sql` undo them on databases that ran them, which is why those files are absent.

- Never edit a migration the owner may already have run; add the next numbered file, make it safe to run twice (`if exists`, `create or replace`, `drop policy if exists`), and update the README's setup list.
- Front-end code that depends on a new migration should be published only after the owner confirms it ran.
- Access is enforced by RLS plus `security definer` functions with explicit `revoke … from public, anon` / `grant` lines; emails and leave notes are hidden by column grants and exposed only through `member_emails()` / `leave_notes()`.
- **Leave from invites** (`011_leave_invites.sql` + `scripts/leave-invites.gs`): a Google Apps Script in a shared Google account reads the invite *emails* (their `invite.ics` attachments: ORGANIZER, dates, SEQUENCE, METHOD:CANCEL) and posts every current leave-like invite to `sync_leave_invites(secret, events)` every 15 minutes. It reads Gmail, not the calendar, because Google imports Outlook invites as events owned by the account itself, which hides the organiser. The list is complete, so invites missing from it count as cancelled; invite leave is keyed by `leaves.invite_uid` (private; the app sees only `from_invite`). Matching uses `profiles.work_email` (private, via `member_work_emails()` / `set_work_email()`) or the sign-in email; misses go to `unmatched_invites` for admins. Removing invite leave in the app would be undone by the next sync, so the UI points people to Outlook instead.
  - What counts as leave is decided in the script (`parseInvite`): all-day events, events of 20 hours or more, and Out of office events (`X-MICROSOFT-CDO-BUSYSTATUS: OOF`) of 4 hours or more. Ordinary meetings are ignored. Leave is whole days only, so a 4-hour Out of office invite takes the person off the roster for that entire day.
  - `set_work_email()` lets approved members set their own and admins set anyone's; people awaiting approval and the public page are refused (`DemoStore.setWorkEmail` mirrors this).
  - The script ignores RRULE, so a recurring invite counts its first occurrence only; deleting an invite email removes its leave.
  - The script runs in Google, not from this repo: pushing a change to `scripts/leave-invites.gs` deploys nothing. The owner must paste the new version into script.google.com in the shared account. The committed file keeps `SCRIPT_SECRET = 'paste-the-script-secret-here'`; the real secret (from `invite_config`) only goes into the Google copy.
- Known gaps, for a later migration: a removed person can still change or delete their own leave through the API (the leave policies don't check `is_member()`); members can set `work_email` directly, bypassing `set_work_email()`; a moved invite whose leave has begun keeps the old start, invites can be forged, one bad invite stops the whole sync, and pending sign-ups can read `settings`.
- `config.js` holds the real project URL and anon key (public by design). To exercise the UI in demo mode, serve the site with an empty `config.js` (e.g. a browser-automation route override) rather than editing the committed file.
